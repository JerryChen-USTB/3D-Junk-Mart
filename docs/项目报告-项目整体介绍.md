# 3dv-junk-mart 项目整体介绍（报告撰写参考）

> 本文档按当前 `3dv-junk-mart` 工作区的真实代码整理，用于后续撰写课程项目报告。  
> 由于部分早期文档来自不同开发阶段，可能存在内容过时、命名变化或编码显示异常，报告中建议以本文档和当前代码结构为主要依据。

## 1. 项目定位

`3dv-junk-mart` 是一个基于 3D Gaussian Splatting（3DGS）的 3D 二手商品交易平台原型。项目试图解决传统二手交易中“图片信息不足、商品细节难判断、买卖沟通成本高”的问题：卖家通过手机录制商品视频，平台将视频交给 3DGS 重建工作链生成可交互 3D 展示资产，买家可以在商品详情中查看商品的 3D 预览，并通过聊天、议价、下单和售后流程完成交易。

当前项目已经从早期“3DGS 发布链路演示”扩展为“3D 商品展示 + 二手电商业务闭环”的综合应用。它的产品形态可以概括为：

- **商品展示侧**：用 3DGS 提供可旋转、可缩放、可校准的商品 3D 展示能力。
- **交易业务侧**：围绕二手交易补齐首页浏览、搜索筛选、收藏、聊天议价、结算下单、模拟支付、发货、收货、退款售后等主链路。
- **系统实现侧**：Flutter 移动端 + FastAPI 后端 + SQLite 业务存储 + 远程 3DGS Trainer Service + Web Viewer。

## 2. 工程来源与当前口径

本项目存在两个需要在报告中区分的阶段：

1. **3DGS 工作链阶段**  
   最初在独立工程 `3DGS-Marketplace` 中完成 3DGS 工作流开发和服务器部署。该阶段重点是视频上传、预处理、COLMAP 位姿恢复、SAM2 Mask、Nerfstudio/Splatfacto 训练、PLY/SOG 导出和 Web Viewer 展示。

2. **电商平台集成阶段**  
   后续将 3DGS 工作链接入 `3dv-junk-mart`，在该工作区中继续开发电商业务、Flutter App、订单系统、聊天议价、个人中心、通知、地址、部署脚本和展示材料。

当前 `3dv-junk-mart` 工作区中有一个 `3dgs-ref/` 目录，它更接近原 `3DGS-Marketplace` 的参考副本，包含完整的 `trainer_service`。而当前主工程根目录主要承载最终产品侧的 Flutter App、FastAPI 业务后端、电商逻辑和与远程训练服务的集成。

报告建议采用以下口径：

- 写 **3DGS 算法流程、训练服务和服务器部署原理** 时，以原 `3DGS-Marketplace` / 当前 `3dgs-ref/` 中的训练服务实现为准。
- 写 **最终系统架构、移动端功能、电商业务闭环和平台集成** 时，以当前 `3dv-junk-mart` 主工程为准。
- 不建议把当前主工程描述为“完整内置训练服务端”。更准确的说法是：主工程通过 `backend/app/services/trainer_service_client.py` 调用远程 3DGS Trainer Service，并将训练结果同步为平台商品。

## 4. 总体架构

当前系统可以分为四层：

1. **Flutter App**
   - 负责用户交互、商品浏览、3D 展示入口、聊天、订单、个人中心和 3DGS 发布流程。
   - 主要代码位于 `app/lib/features/`。
   - 底部主导航由 `app/lib/features/shell/app_shell.dart` 组织，包含首页、搜索、发布、消息、我的五个入口。

2. **FastAPI 业务后端**
   - 入口为 `backend/app/main.py`。
   - 挂载两个主要路由：
     - `backend/app/routes/marketplace.py`：电商业务 API。
     - `backend/app/routes/reconstructions.py`：3DGS 任务、发布和 Viewer 校准 API。
   - 后端同时挂载 `/storage`、`/viewer` 静态资源，并提供 `/proxy/storage/*` 代理远程训练服务的模型文件。

3. **远程 3DGS Trainer Service**
   - 当前主工程通过 `backend/app/services/trainer_service_client.py` 调用远程训练服务。
   - 服务地址由 `GS_SERVICE_BASE_URL` / `TRAINER_SERVICE_BASE_URL` 配置，当前 README 中示例为 `http://222.199.216.192:9000`。
   - 完整训练服务参考实现位于 `3dgs-ref/trainer_service/`。

4. **存储层**
   - 电商业务数据使用 SQLite，路径由 `SQLITE_DB_PATH` 或默认 `storage/db/business.db` 决定。
   - 3DGS 任务元数据使用 `storage/tasks/*.json`。
   - 上传视频、处理中间产物和训练模型分别存放在 `storage/uploads/`、`storage/processed/`、`storage/models/`。

简化架构如下：

```text
Flutter App
  | REST API
  v
FastAPI Backend (:8000)
  |-- marketplace API -> SQLite business records
  |-- reconstructions API -> local task JSON + remote trainer client
  |-- /viewer static files
  |-- /proxy/storage/* -> remote trainer storage
  v
Remote 3DGS Trainer Service (:9000)
  |-- video preprocessing
  |-- COLMAP pose estimation
  |-- SAM2 object masking
  |-- Nerfstudio/Splatfacto training
  |-- PLY/SOG export
```

## 6. 后端业务能力

### 6.1 Marketplace API

`backend/app/routes/marketplace.py` 是当前电商业务的核心文件，路由前缀为 `/api/v1`。它覆盖：

- 用户认证、游客会话、个人资料、头像上传。
- 首页、搜索、商品列表、商品详情、收藏、评价。
- 聊天会话、消息、议价单创建/接受/拒绝。
- 订单创建、模拟支付、发货、确认收货、取消订单、申请退款、同意退款、拒绝退款、纠纷。
- 钱包、会员、通知、地址管理。
- 页面级 bootstrap 接口，例如 `/pages/home`、`/pages/orders`、`/pages/messages` 等。

订单主状态已经从简单 MVP 状态扩展为较完整的交易状态机：

```text
pending_payment -> awaiting_shipment -> shipped -> completed
       |                  |               |
       v                  v               v
   cancelled       refund_requested   refund_requested
                          |
                          v
                  refunded / disputed
```

订单还拆分了支付、履约、售后等维度的状态字段，例如 `payment_status`、`shipping_status`、`aftersale_status`。这使订单详情页可以展示更接近真实电商平台的信息卡片和操作按钮。

### 6.2 Reconstruction API

`backend/app/routes/reconstructions.py` 路由前缀为 `/api/v1/reconstructions`，负责把 3DGS 工作链接入电商发布流程。它覆盖：

- 创建重建任务并上传视频。
- 调用远程 Trainer Service 创建任务、启动训练、取消训练。
- Mask 预览、Mask 确认和 Mask Debug。
- 上传商品封面。
- Viewer 校准状态保存，包括旋转、平移、初始视角和动画确认。
- 发布重建结果为 marketplace listing。
- 根据已发布任务自动创建或更新商品记录。

这一层不是纯训练算法实现，而是“业务后端与远程训练服务之间的集成层”。它额外处理用户鉴权、卖家归属、任务所有权校验、模型 URL 映射、远程资源代理和电商商品同步。

## 7. 3DGS 工作链

项目中的 3DGS 工作链可以按以下阶段描述：

1. **视频采集**
   - 卖家围绕商品拍摄短视频。
   - Flutter 发布流程将视频提交给后端。

2. **视频预处理**
   - 使用 FFmpeg / ffprobe 做视频元数据校验、抽帧和分辨率处理。
   - 根据质量档位控制训练成本和输出质量。

3. **COLMAP 位姿恢复**
   - 从视频帧中恢复相机位姿，为后续 3DGS 训练提供 SfM 结果。

4. **对象 Mask**
   - 可使用 SAM2 对商品前景做交互式 Mask。
   - 用户在移动端点选商品区域，后端/训练端生成 Mask 预览，确认后继续训练。

5. **3DGS 训练**
   - 使用 Nerfstudio/Splatfacto 训练 3D Gaussian Splatting 表示。
   - 支持不同质量档位和训练步数配置。

6. **模型导出**
   - 导出 PLY 模型。
   - 可进一步转换为 SOG 格式，降低 Web 端加载成本。

7. **Viewer 校准**
   - 在发布前调整模型旋转、平移、默认视角和展示动画。
   - 校准完成后发布为平台商品。

8. **商品展示**
   - 商品卡片默认展示封面图。
   - 商品详情或 3D 入口通过 Web Viewer 加载 `.ply` / `.sog` 模型。

报告中应说明：3DGS 训练端最初在 `3DGS-Marketplace` 中部署；当前主工程通过远程调用方式集成该能力，并围绕商品发布流程增加了业务控制。

## 8. 3D Viewer

`viewer/` 目录提供 Web 端 3D 展示页面，核心文件包括：

- `viewer/index.html`
- `viewer/viewer.js`
- `viewer/style.css`
- `viewer/model-cache.js`
- `viewer/cache-manager.js`

Viewer 的作用是加载训练生成的 3DGS 模型资产，并提供旋转、缩放、校准和展示能力。Flutter 端通过 WebView 打开 Viewer 页面。后端提供 `/viewer` 静态挂载和 `/proxy/storage/*` 远程模型代理，解决移动端在 USB 调试或网络受限情况下访问远程模型文件的问题。

## 9. 数据与存储设计

当前项目采用轻量化存储方案：

1. **电商业务数据**
   - 使用 SQLite。
   - 核心表是通用 `records` 表，通过 `entity_type`、`entity_id`、`parent_id` 和 JSON payload 存储不同实体。
   - 实体包括用户、资料、商品、收藏、会话、消息、议价单、订单、物流、评价、钱包、会员、通知、地址等。
   - 相关代码位于 `backend/app/services/marketplace_store.py`。

2. **3DGS 任务数据**
   - 使用 JSON 文件保存任务状态。
   - 相关代码位于 `shared/task_store.py`。
   - 这种方式方便训练流水线进程直接读写任务状态，但生产系统中仍可进一步迁移到数据库或任务队列。

3. **文件资产**
   - 视频、封面、头像、模型、训练日志和中间结果都存放在 `storage/` 下。
   - 部署时可通过 `STORAGE_ROOT` 指向服务器数据盘。

这种设计更适合课程项目、单机部署和演示环境，优点是实现简单、便于调试；缺点是并发能力、查询能力和数据治理能力有限。

## 10. 当前已实现的核心业务链路

### 10.1 买家链路

```text
登录/游客浏览
  -> 首页浏览 / 搜索筛选
  -> 商品详情 / 3D 预览
  -> 收藏 / 联系卖家
  -> 聊天议价
  -> 确认订单
  -> 模拟支付
  -> 等待卖家发货
  -> 查看物流 / 确认收货
  -> 评价或申请退款
```

### 10.2 卖家链路

```text
登录
  -> 发布入口
  -> 上传商品视频
  -> 启动 3DGS 重建
  -> Mask 交互和 Viewer 校准
  -> 发布为商品
  -> 与买家聊天/处理议价
  -> 查看订单
  -> 发货
  -> 处理退款或售后
```

### 10.3 议价链路

```text
买家发起议价
  -> 卖家接受/拒绝
  -> 买家看到成交价
  -> 买家按成交价下单
```

当前实现中，一个会话同一时刻主要围绕一个活跃议价单处理。卖家接受后，买家聊天页会显示成交价格，并允许买家按成交价进入结算；卖家侧不会显示“去下单”。

### 10.4 售后链路

```text
待发货/已发货订单
  -> 买家申请退款
  -> 卖家同意退款 / 拒绝退款
  -> 同意后订单进入已退款
  -> 商品恢复为可售状态
```

当前售后实现是基础版，重点覆盖退款申请、卖家处理、状态更新和商品释放，不包含真实资金通道、退货物流和图片举证。

## 13. 当前实现边界

报告中建议客观说明以下边界：

- **支付是模拟支付**：项目不接入真实支付渠道，订单支付通过 mock pay 完成。
- **售后是基础版**：支持退款申请、卖家同意/拒绝、纠纷状态，但不包含真实退款通道、退货物流和举证系统。
- **训练服务依赖远程环境**：新建 3DGS 训练任务需要远程 Trainer Service 可访问；离开校园网或服务器不可达时，只能验证已有模型展示和电商业务。
- **数据存储偏 MVP**：电商数据使用 SQLite + JSON payload，适合课程项目和单机部署，不是高并发生产级数据库设计。
- **3DGS 训练端来源需区分**：训练端完整实现来自原 `3DGS-Marketplace` / `3dgs-ref`，当前主工程主要负责集成和业务化。
- **UI 已面向展示优化，但不是最终商业级产品**：首页、搜索、聊天、订单和个人中心已达到较完整展示效果，但仍有继续统一设计语言、完善异常态和国际化/中文编码清理的空间。

## 14. 报告撰写建议结构

可以按以下结构撰写课程报告：

1. **项目背景与问题定义**
   - 二手交易中商品细节难判断。
   - 传统图文展示无法充分表达商品三维信息。
   - 引入 3DGS 改善商品可信展示和浏览体验。

2. **总体方案**
   - Flutter App + FastAPI 后端 + 远程 3DGS Trainer Service + Web Viewer。
   - 3DGS 展示链路与电商交易链路结合。

3. **3DGS 工作流设计**
   - 视频采集、预处理、COLMAP、SAM2、训练、导出、Viewer 校准、发布。
   - 说明训练端来自原 `3DGS-Marketplace`，当前项目完成业务集成。

4. **电商业务设计**
   - 首页、搜索、详情、收藏、聊天议价、订单、物流、退款、个人中心。
   - 重点说明订单状态机和议价到下单的闭环。

5. **系统实现**
   - 前端模块、后端 API、存储设计、远程训练服务调用、Viewer 代理。

6. **测试与展示**
   - 后端矩阵测试、Flutter 测试、部署健康检查。
   - 展示截图和操作视频可按“浏览 -> 详情 -> 聊天议价 -> 下单 -> 发货 -> 退款/收货 -> 3DGS 发布”组织。

7. **不足与展望**
   - 真实支付、生产级数据库、异步任务队列、售后举证、模型质量评估、性能优化、部署自动化。

## 15. 一句话总结

`3dv-junk-mart` 的核心价值在于把 3DGS 从单纯的三维重建演示，进一步放入二手交易场景中，形成“手机采集商品视频 -> 远程 3DGS 重建 -> 3D 商品展示 -> 聊天议价 -> 下单履约”的完整产品原型。

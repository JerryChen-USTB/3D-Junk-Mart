# 训练服务拆分与团队协作开发方案

更新时间：2026-04-09  
适用代码仓库：`d:\Projects\3dgs-app`  
目标：把 3DGS 训练能力统一部署到服务器，并把它封装成一个远程 3DGS 服务；团队成员继续在本地开发前端和业务后端，不需要配置训练环境，也不需要接触训练细节。

> 本文档是新的目标方案。  
> 它明确**不采用共享 storage**，也不要求团队成员把业务后端部署到服务器上。

---

# 1. 背景与团队真实需求

## 1.1 当前项目的形态

当前 MVP 是一个本机单体方案：

1. Flutter App 上传视频到 FastAPI
2. FastAPI 在本机保存视频和任务
3. FastAPI 在本机直接启动 `trainer/pipeline.py`
4. 本机继续调用 COLMAP、SAM2、nerfstudio、导出工具
5. 结果写回本机 `storage/`
6. FastAPI 再把模型和 viewer 暴露给 App

这套方案适合你个人验证，但不适合团队接业务开发。

## 1.2 团队成员真正想要的是什么

团队成员不想理解这些内容：

1. COLMAP
2. SAM2
3. nerfstudio
4. CUDA / GPU 环境
5. 训练脚本怎么启动
6. 模型是怎么导出的

他们真正需要的是一个黑盒能力：

1. 上传一个视频
2. 拿到一个 `task_id`
3. 查询训练进度
4. 训练完成后拿到模型标识、模型 URL 或 `viewer_url`
5. 在页面里把它显示出来

换句话说，对业务同学来说，3DGS 应该是一个**远程服务**，不是一个要在每台开发机上配置完整环境的工程体系。

## 1.3 这次方案的关键约束

这次方案必须满足以下约束：

1. **业务后端不能部署在服务器上**
   - 团队成员还需要本地编写、调试业务后端代码
2. **不采用共享 storage**
   - 本地后端和服务器之间不共享文件目录
   - 不要求团队成员挂载共享盘、同步 `storage/`
3. **团队成员本地不安装训练环境**
   - 不装 COLMAP
   - 不装 CUDA
   - 不装 nerfstudio
   - 不装 SAM2

# 2. 方案结论

## 2.1 最终推荐方案

推荐把系统拆成两套后端：

1. **业务后端（本地开发）**
2. **3DGS 服务（服务器部署）**

其中：

- 团队成员继续在本地开发业务后端
- 训练、模型存储、viewer、任务进度都放到服务器上的 3DGS 服务
- 本地业务后端通过 HTTP 调用远程 3DGS 服务
- 本地业务后端不直接访问服务器文件系统
- 本地业务后端也不保存训练中间产物

## 2.2 一句话理解

从团队视角来看：

**3DGS 是一个远程能力服务，不是本地工程依赖。**

业务后端只负责“调用它”，不负责“运行它”。

# 3. 推荐架构

## 3.1 总体拓扑

```text
Flutter App
   |
   v
业务后端（团队本地开发 / 业务环境部署）
   |
   | HTTP / HTTPS
   v
远程 3DGS 服务（服务器）
   |
   +--> 训练执行（COLMAP / SAM2 / nerfstudio / 导出）
   +--> 任务状态存储
   +--> 模型文件存储
   +--> viewer 静态托管
```

## 3.2 各部分职责

### 业务后端

负责：

1. 电商业务接口
2. 商品数据管理
3. 用户、订单、商品详情等业务逻辑
4. 调用远程 3DGS 服务
5. 保存 3DGS 任务 ID、模型 ID、viewer URL 等引用信息

不负责：

1. 训练
2. Mask 生成
3. 模型导出
4. 存储训练中间文件

### 远程 3DGS 服务

负责：

1. 接收视频上传
2. 创建 3DGS 任务
3. 管理训练状态
4. 运行 Masking、训练、导出、对象提取
5. 返回任务进度
6. 返回 `model_url` / `viewer_url`
7. 托管模型文件和 viewer

### Flutter App

推荐仍然通过业务后端接入，不直接耦合 3DGS 服务。  
这样业务后端可以统一封装业务逻辑和权限控制。

# 4. 为什么不能采用共享 storage

共享 storage 虽然在工程上改动更小，但不符合团队实际诉求，主要问题有：

1. 团队成员需要理解和维护额外的目录同步逻辑
2. 本地后端和服务器训练服务会形成文件系统耦合
3. 本地联调和服务器联调的行为差异会变大
4. 一旦文件结构或挂载方式变化，业务后端也会被牵连
5. 团队成员并不关心训练文件怎么落盘，他们只关心 API 输入输出

因此，这次方案明确采用：

**远程 3DGS 服务自己管理自己的文件与模型，不对业务后端暴露文件系统。**

# 5. Git 怎么处理

## 5.1 继续保留完整单仓库

当前阶段**不建议拆仓**。  
建议继续保留 monorepo：

1. `mobile_app/`
2. `backend/`
3. `trainer/`
4. `shared/`
5. `viewer/`
6. `docs/`

原因：

1. 当前代码仍然有大量共享逻辑
2. 现在最重要的是拆“部署形态”和“运行职责”，不是先拆 Git
3. 提前拆仓会增加协作成本

## 5.2 但部署单元要拆开

虽然 Git 保持单仓库，但部署时要拆成两个单元：

### 单元 A：业务后端

由团队成员本地开发、测试、部署。

### 单元 B：3DGS 服务

部署在服务器上，只由负责 3DGS 基础设施的同学维护。

## 5.3 分支建议

推荐：

1. `main`：稳定主线
2. `feature/*`：功能分支
3. `staging`：服务器联调分支（可选）

原则：

1. 团队成员在本地开发并提 PR
2. 服务器只部署固定分支
3. 不在服务器上直接改代码提交

# 7. 3DGS 服务对业务后端暴露的最小契约

这是团队最需要的部分。  
无论内部怎么训练，对外应只暴露以下能力。

## 7.1 创建任务并上传视频

```text
POST /tasks
```

输入：

1. 视频文件
2. 可选配置：质量档位、训练轮数、是否 Object Masking

返回：

```json
{
  "task_id": "task_xxx",
  "status": "uploaded"
}
```

## 7.2 查询任务状态

```text
GET /tasks/{task_id}
```

返回：

```json
{
  "task_id": "task_xxx",
  "status": "training",
  "progress": 62,
  "status_message": "正在训练",
  "viewer_url": null,
  "model_url": null
}
```

如果完成：

```json
{
  "task_id": "task_xxx",
  "status": "ready",
  "progress": 100,
  "viewer_url": "https://3dgs.example.com/viewer/index.html?...",
  "model_url": "https://3dgs.example.com/storage/models/task_xxx/model.sog"
}
```

## 7.3 Mask 交互接口

如果业务上保留 Object Masking：

1. 生成预览
2. 提交点位
3. 确认继续

这些也都应该由远程 3DGS 服务提供 API，业务后端只负责转发和封装。

## 7.4 模型消费方式

业务后端和前端只关心：

1. `task_id`
2. `status`
3. `progress`
4. `model_id`（可选）
5. `model_url`
6. `viewer_url`

不需要知道：

1. 模型文件在服务器什么目录
2. 中间产物长什么样
3. 训练命令怎么执行

# 8. 业务后端如何接远程 3DGS 服务

## 8.1 推荐接法

业务后端作为统一入口，负责和远程 3DGS 服务交互。

也就是：

1. Flutter App -> 业务后端
2. 业务后端 -> 远程 3DGS 服务

这样团队成员只需要理解一套业务 API。

## 8.2 上传视频的推荐方式

有两种方式：

### 方式 A：业务后端接收后转发给 3DGS 服务

流程：

1. App 把视频传给业务后端
2. 业务后端把同一个文件再转发给远程 3DGS 服务
3. 3DGS 服务创建任务
4. 业务后端保存 `task_id`

优点：

1. 业务后端可以完全掌控上传流程
2. App 不需要知道 3DGS 服务地址
3. 权限、鉴权、日志都更统一

缺点：

1. 视频会经过业务后端一次

### 方式 B：业务后端签发参数，App 直传 3DGS 服务

流程：

1. App 先向业务后端申请上传授权
2. 业务后端返回远程 3DGS 服务的上传参数
3. App 直接上传到 3DGS 服务

优点：

1. 业务后端压力更小

缺点：

1. 实现复杂度更高
2. 当前 MVP 阶段没有必要先走这条

## 8.3 当前阶段推荐

**当前阶段推荐方式 A：业务后端接收后转发。**

因为它最符合团队现在的开发习惯，最容易落地，也最便于调试。

---

# 9. 服务器上的 3DGS 服务应该长什么样

## 9.1 推荐拆成两层

远程 3DGS 服务内部可以继续拆成：

1. **3DGS API**
2. **Trainer Worker**

### 3DGS API

负责：

1. 接收视频
2. 创建任务
3. 查询任务状态
4. 提供 Mask 接口
5. 提供 `viewer_url`
6. 提供模型下载地址

### Trainer Worker

负责：

1. 真正执行 `trainer.pipeline`
2. 跑 COLMAP / SAM2 / nerfstudio / 导出
3. 回写任务状态

## 9.2 文件与模型存储位置

远程 3DGS 服务可以先继续使用服务器本地的 `storage/`，但这个 `storage/` 是**服务内部实现细节**：

1. 只存在于服务器
2. 不对本地业务后端暴露
3. 不要求团队成员同步或挂载

从团队视角，它只是服务内部的磁盘目录，不再是协作边界。

# 10. 代码结构建议

## 10.1 推荐目标

把当前代码逻辑上的角色拆清楚：

### A. 业务后端

保留：

1. 商品业务逻辑
2. 用户流程
3. 与远程 3DGS 服务的调用封装

### B. 3DGS 服务

承接：

1. 当前 `backend/app/routes/reconstructions.py` 中与训练强相关的部分
2. 当前 `trainer/`
3. 当前 `viewer/`
4. 当前模型和任务状态接口

## 10.2 推荐新增模块

### 1. `backend/app/services/gs_client.py`

作用：

1. 封装业务后端对远程 3DGS 服务的 HTTP 调用
2. 提供：
   - `create_task`
   - `get_task`
   - `cancel_task`
   - `preview_mask`
   - `confirm_mask`

### 2. `gs_service/`

建议新增目录：

```text
gs_service/
  app.py
  routes/
  schemas.py
  services/
```

它是远程 3DGS 服务的 API 层。

### 3. `trainer_worker/` 或沿用 `trainer/worker.py`

让训练执行进程由服务器侧 worker 承担，而不是业务后端承担。

## 10.3 当前代码中的迁移方向

### 当前 `backend/app/routes/reconstructions.py`

需要逐步拆成两部分：

1. **业务后端保留的内容**
   - 业务封装
   - 对 3DGS 服务的调用

2. **迁移到远程 3DGS 服务的内容**
   - 上传视频后的训练任务管理
   - Mask preview
   - mask confirm
   - 真训练启动 / 取消
   - viewer URL 组装
   - 模型文件托管

# 11. 开发与部署方案

## 11.1 团队成员本地开发模式

团队成员本地运行：

1. 业务后端
2. Flutter App

配置：

1. 业务后端配置远程 `3DGS_SERVICE_BASE_URL`

1. COLMAP

3. SAM2

## 11.2 服务器部署模式

服务器运行：

1. 远程 3DGS API
2. Trainer Worker
3. viewer 静态服务
4. 服务器本地 `storage/`

## 11.3 这样做的结果

团队成员开发业务时：

1. 只需要业务后端和 Flutter 环境
2. 真训练统一走服务器
3. viewer 和模型文件统一走服务器 URL

# 12. 多人协作策略

## 12.1 推荐协作方式

推荐方式是：

2. 大家共用一个远程 3DGS staging 服务

1. 多人共用服务器开发业务后端
2. 本地和服务器之间同步 `storage/`
3. 让业务同学直接碰训练脚本

# 13. 分阶段实施方案

## 阶段 A：先把 3DGS 能力封装成远程服务

目标：

1. 团队继续本地开发业务后端
2. 训练统一在服务器
3. 本地不配置训练环境

需要完成：

1. 新建远程 3DGS API
2. 把训练启动、取消、Masking、viewer 相关能力迁到远程服务
3. 让服务器自己管理上传视频、任务状态、模型文件

产出：

1. 一个独立的 3DGS 服务地址
2. 一套稳定的任务 API

## 阶段 B：业务后端接入远程 3DGS 服务

需要完成：

1. 业务后端新增 `gs_client`
2. 上传视频时转发到远程 3DGS 服务
3. 保存远程 `task_id`
4. 轮询远程任务状态
5. 把 `viewer_url` / `model_url` 回传给前端

## 阶段 C：前端联调

需要完成：

1. App 仍然只调用业务后端
2. 前端根据业务后端返回的 `status / progress / viewer_url` 展示状态和模型

## 阶段 D：长期升级

后续再考虑：

1. 任务状态改数据库
2. 模型文件改对象存储
3. 上传改成直传
4. worker 队列化

# 16. 验收标准

这套方案落地后，应满足以下验收标准：

1. 团队成员本地不安装训练环境，仍能正常开发业务后端和 Flutter
2. 本地业务后端可成功调用远程 3DGS 服务创建任务

4. 本地业务后端可获取 `viewer_url` / `model_url`
5. Flutter 页面能继续展示进度、进入 viewer、查看模型
6. 全流程不依赖共享 storage

# 17. 一句话总结

这次方案的核心不是“把业务后端也搬上服务器”，而是：

**把 3DGS 流水线封装成一个远程服务，让业务后端继续留在团队本地开发环境中，只通过 API 使用它。**

这样可以同时满足：

1. 团队成员继续开发业务后端
2. 团队成员不配置训练环境
3. 不引入共享 storage
4. 3DGS 仍然能作为稳定能力提供给业务系统

# 18. 推荐下一步

建议接下来按下面顺序推进：

1. 先明确“远程 3DGS 服务”的最小 API 契约
2. 再把当前训练相关 FastAPI 能力从业务后端中拆出去
3. 在服务器部署第一版远程 3DGS 服务
4. 最后让业务后端接入这个远程服务

只要这四步完成，团队就能进入“本地写业务，远程用 3DGS”的工作模式。

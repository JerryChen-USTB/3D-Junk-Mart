# 远程 3DGS 服务迁移清单

更新时间：2026-04-09  
适用仓库：`d:\Projects\3dgs-app`

> 本文档是基于当前 `main` 已完成的“训练服务拆分过渡版本”整理出的迁移清单。  
> 它不替代 [18-训练服务拆分与团队协作开发方案.md](/d:/Projects/3dgs-app/docs/18-%E8%AE%AD%E7%BB%83%E6%9C%8D%E5%8A%A1%E6%8B%86%E5%88%86%E4%B8%8E%E5%9B%A2%E9%98%9F%E5%8D%8F%E4%BD%9C%E5%BC%80%E5%8F%91%E6%96%B9%E6%A1%88.md)，而是回答一个更具体的问题：
>
> **如何从“HTTP 调训练服务 + 共享 storage”过渡到“远程训练服务自管理任务与模型、业务后端继续本地托管 viewer”的正式方案。**

## 1. 当前 main 应如何看待

当前 main 不应该再被理解成最终方案，而应该被理解为：

**一个已经完成“控制面拆分”的过渡阶段成果。**

它已经做对的部分：

1. 业务后端不再直接本机启动训练脚本
2. 已有 `trainer_service/` 可承接训练启动、取消、Mask preview、resume
3. 已有 `backend/app/services/trainer_client.py` 作为 HTTP 调用封装
4. 训练配置、状态枚举等纯逻辑已经从 `trainer.pipeline` 中下沉到了共享模块

它还没有做对的部分：

1. `backend` 和 `trainer_service` 仍然共享 `shared.task_store`
2. `backend` 仍然把 `storage/` 当成自己的本地数据源
3. `trainer_service` 仍然假设任务 JSON、上传视频、中间产物与模型文件都与 `backend` 在同一个 `STORAGE_ROOT`
4. `viewer_url` / `model_url` 的组装仍然混杂着本地 `viewer/` 与共享 `storage/` 假设

所以，当前 main 的价值主要在于：

**已经证明“业务后端通过 HTTP 调训练服务”这条方向是对的。**

## 2. 当前哪些成果可以保留

这些内容建议保留并继续演进：

### 2.1 `trainer_service/`

可保留原因：

1. 它已经把训练进程管理从业务后端分离出来
2. 已经具备最核心的训练控制能力
3. 后续完全可以继续演进成“远程 3DGS 服务”的一部分

建议保留的能力：

1. `start`
2. `cancel`
3. `mask-preview`
4. `mask-confirm / resume`
5. `mask-debug`

### 2.2 `backend/app/services/trainer_client.py`

可保留原因：

1. 它已经把 HTTP 调用从路由层抽出来
2. 调用超时、错误映射、认证头封装的方向是对的

后续建议：

1. 保留现有 `trainer_client` 作为过渡兼容层
2. 新增更贴近正式方案的 `gs_client`
3. 逐步把业务后端从“内部训练控制接口”迁到“远程 3DGS 任务接口”

### 2.3 `shared/training_config.py` 与 `shared/task_status.py`

可保留原因：

1. 它们属于纯配置 / 纯校验逻辑
2. 不依赖共享 storage
3. 对业务后端和远程 3DGS 服务都仍然有价值

## 3. 当前哪些地方仍然绑着共享 storage

这些是下一阶段需要优先拆掉的地方：

### 3.1 `shared/task_store.py`

问题：

1. 它默认把任务系统实现成基于本地文件的共享事实源
2. `backend` 和 `trainer_service` 都直接读写同一套任务 JSON
3. `video_rel_path / model_rel_path / log_rel_path` 都假设路径可以从共享磁盘推导

结论：

1. `task_store` 可以继续留给远程 3DGS 服务内部使用
2. 但业务后端不能再把它当成自己与训练服务之间的协作边界

### 3.2 `backend/app/routes/reconstructions.py`

当前已完成的拆分：

1. 上传视频已经改成业务后端转发给远程训练服务
2. 列表、详情、开始、取消、Mask、删除都已经通过 `gs_client` 走远程 API
3. `model_url` 已经直接来自远程训练服务
4. `viewer_url` 已经改为业务后端基于本地 `viewer/` 与远程 `model_url` 动态生成

当前仍然保留的过渡层：

1. 业务后端本地仍然保存远程任务镜像
2. 发布流业务态仍然保存在本地 `task_store`

### 3.3 `trainer_service/services/runtime.py`

当前仍然绑共享 storage 的点：

1. 启动训练前通过 `get_task()` 读取共享任务 JSON
2. 通过 `video_rel_path -> STORAGE_ROOT` 定位上传视频
3. 通过 `update_task()` 直接修改共享任务 JSON
4. `mask-preview` 和 `resume` 依赖共享 `processed/`、`models/`、`tasks/`

结论：

1. 这些行为对“远程 3DGS 服务内部”仍然成立
2. 真正要去掉的不是服务内部的 `storage/`，而是**业务后端对它的依赖**

## 4. 新旧边界的正确拆法

下一步不应该直接去动训练算法，而应该先拆清楚**谁拥有数据真相**。

### 4.1 业务后端保留什么

业务后端应保留：

1. 业务数据
2. 商品流程
3. 远程 3DGS `task_id` 引用
4. `viewer_url` / `model_url` / `status` 的业务侧镜像
5. 本地 `viewer/` 静态托管
6. 对远程 3DGS 服务的 HTTP 封装

业务后端不再保留：

1. 训练中间文件
2. 训练上传视频文件
3. 训练任务 JSON 真相源
4. 训练模型文件
5. viewer 静态资源本体

### 4.2 远程 3DGS 服务接管什么

远程 3DGS 服务需要接管：

1. 上传视频并创建任务
2. 任务状态真相源
3. 训练进度管理
4. Mask preview / confirm
5. 取消任务
6. 模型存储
7. Viewer 配置存储
8. `model_url` 返回

## 5. 推荐迁移顺序

### 第 1 步：先补齐远程 3DGS 服务公开 API

目标：

1. 让 `trainer_service` 不只是“内部控制面”
2. 还要能作为“远程 3DGS 服务 API”对外提供任务接口

最少需要：

1. `POST /tasks`
2. `GET /tasks/{task_id}`
3. `POST /tasks/{task_id}/start`
4. `POST /tasks/{task_id}/cancel`
5. `POST /tasks/{task_id}/mask-preview`
6. `POST /tasks/{task_id}/mask-confirm`

当前仓库已落地的最小实现：

1. `trainer_service` 已新增公开 `POST /tasks`、`GET /tasks`、`GET /tasks/{task_id}`
2. `trainer_service` 已新增公开 `start / cancel / mask-debug / mask-preview / mask-confirm`
3. `trainer_service` 目前只公开 `/storage`，不再承载 viewer 静态资源
4. 业务后端的创建任务、列表、详情、`start / cancel / mask-debug / mask-preview / mask-confirm / delete / viewer-update` 已切到公开 `gs_client`
5. 业务后端本地 `task_store` 现在主要承担“远程任务镜像 + 发布流业务态”角色
6. Flutter 最终拿到的 `viewer_url` 由业务后端本地 `viewer/` 生成，但其中的 `model` 参数指向远程训练服务的 `model_url`
7. 这意味着共享 `storage` 现在可以被理解成**远程训练服务内部实现**，而不再是推荐的跨服务协作边界

### 第 2 步：新增业务后端的 `gs_client`

目标：

1. 不再让业务后端面向 `trainer_service` 的内部接口编程
2. 而是面向“远程 3DGS 服务的公开任务 API”编程

### 第 3 步：业务后端的创建任务逻辑改成“接收后转发”

迁移前：

1. App -> 业务后端
2. 业务后端保存视频到本地 `storage/uploads`
3. 业务后端创建本地任务 JSON

迁移后：

1. App -> 业务后端
2. 业务后端把视频转发给远程 3DGS 服务
3. 远程 3DGS 服务创建远程任务
4. 业务后端只保存远程 `task_id`

### 第 4 步：业务后端把任务详情改成“远程状态镜像”

迁移前：

1. 业务后端 `GET task` 直接读本地 JSON

迁移后：

1. 业务后端 `GET task` 调远程 3DGS 服务
2. 再把结果映射到业务后端自己的返回模型

### 第 5 步：去掉业务后端对本地 `/storage` 作为训练事实源的依赖

迁移前：

1. `viewer_url` 和 `model_url` 都混在本地任务文件逻辑中组装

迁移后：

1. `model_url` 来自远程训练服务
2. `viewer_url` 由业务后端基于本地 `viewer/` 和远程 `model_url` 动态组装

## 6. 这一步不该做什么

在当前阶段，不建议先做这些事：

1. 不要先改训练算法
2. 不要先重构 `trainer.pipeline` 的训练细节
3. 不要先引入数据库或对象存储
4. 不要先把 `trainer_service` 推倒重写
5. 不要回退 main 上已经完成的 HTTP 化成果

## 7. 当前阶段最合理的代码动作

当前阶段最合理的是：

1. 保留现有 `trainer_service` 作为训练控制核心
2. 在它外面补一层面向正式架构的“远程任务 API”
3. 在业务后端补 `gs_client`
4. 让业务后端逐步从 `trainer_client` 迁到 `gs_client`

## 8. 当前还未完成的后续工作

完成这轮边界拆分后，仍然需要继续做：

1. 业务后端本地 `task_store` 的角色调整
2. 远程任务 ID 与本地业务对象的持久化映射
3. 远程服务鉴权
4. 远程 viewer 域名与静态资源部署
5. 长期的数据库 / 对象存储演进

## 9. 一句话总结

当前 main 最值得保留的是：

**“业务后端通过 HTTP 调训练服务”这个方向已经跑通。**

下一步真正要做的，不是回退它，而是：

**让远程 3DGS 服务自己拥有任务、文件、模型和 viewer，业务后端只保留业务侧引用与状态镜像。**
